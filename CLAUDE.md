# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SailBoard is a Windows + macOS clipboard history tool (Linux is explicitly out of scope) built with Go + Wails v2 + React/TypeScript. It renders as a full-screen-width, iOS-style light frosted-glass sheet that slides up from the bottom of the screen (not a floating window), showing recent clipboard items as a horizontal card rail with search, favorites, and automatic cleanup by retention days / max storage size. Both platforms are full native apps with feature parity: global hotkey summon, auto-positioned bottom panel, auto-paste-back into whatever app had focus, image clipboard support, source-app icons, a tray/menu-bar icon, and launch-at-login.

`progress.md` tracks what's actually implemented and any known limitations — every `internal/platform.Controller` method is a real native implementation on both Windows and macOS now; only genuinely other platforms (which this project doesn't target) fall back to the no-op stub.

## Commands

```powershell
# Go tests (run from repo root)
go test ./...
go test ./internal/clipboard/...              # single package
go test ./internal/storage/... -run TestName  # single test

# Frontend
cd frontend
npm install
npm run build      # tsc + vite build; must pass before `wails build`

# Full dev loop (desktop app + frontend hot reload)
wails dev

# Regenerate frontend/wailsjs bindings after changing App method signatures, without a full build
wails generate module

# Production build (Windows) -> build/bin/SailBoard.exe
wails build

# Production build (macOS, from a Mac — needs a recent Xcode Command Line Tools SDK; see
# README.md's macOS build section for the CGO_LDFLAGS workaround this Wails version needs)
CGO_LDFLAGS="-framework UniformTypeIdentifiers" wails build -platform darwin/arm64 -clean
# -> build/bin/SailBoard.app; package into a DMG with build/darwin/package-dmg.sh
```

There is no lint script configured; TypeScript compilation (`tsc` via `npm run build`) is the only frontend check. On Windows, `go vet ./...` reports eight `possible misuse of unsafe.Pointer` findings across `internal/platform/clipboard_image_windows.go`, `clipboard_files_windows.go`, and `clipboard_richtext_windows.go` — all are the standard "convert a Win32 GlobalLock address to a byte slice" pattern for foreign (non-Go-managed) memory, commented in place, and not real bugs; `go test` doesn't run that vet check so they don't fail the test suite. This count grows by two (a read + a write helper) each time a new clipboard format gets its own GlobalLock-based reader/writer — check the finding locations still match known GlobalLock call sites before assuming a new one is one of these, rather than a real bug. On macOS, `go vet ./...`/`go build` succeeding is a much weaker signal than on Windows — see the `internal/platform/` bullet below for five real bugs that were fully invisible to both and only showed up running the packaged app.

## Architecture

The project deliberately keeps four core objects decoupled, with dependencies flowing one direction only:

```
UI (React)
 ↓
App API (app.go — Wails-bound methods, DTO translation, orchestration)
 ↓
Service (internal/clipboard.Service — capture/dedup/paste logic)
 ↓
Repository / Platform interfaces (internal/storage, internal/platform)
 ↓
SQLite / Win32 APIs
```

Never let React, OS-specific code, or SQLite couple directly to each other — always go through the Service/Repository/Controller interfaces. This is a hard architectural constraint, not a stylistic preference: it's what let `internal/platform` add a real macOS backend (`controller_darwin.go` + friends) without touching `app.go` or `internal/clipboard` at all — the same interface Windows had already been driving through.

- **`app.go`** — the only Wails-bound surface, and the orchestration layer that wires `internal/clipboard`, `internal/storage`, and `internal/platform` together. Owns app lifecycle (`startup`/`shutdown`), builds the `clipboard.Watcher` (native image+sequence-number reads when `platform.Controller` is available, falling back to Wails' `runtime.ClipboardGetText` text-diff polling otherwise), registers the global hotkey, positions the window on show (`ShowWindow`), restores focus and sends the paste keystroke (`PasteItem`), and converts `clipboard.Item` → `ClipboardItemDTO` for the frontend (inlining the source-app icon as a `data:` URI; image bytes are fetched lazily via `GetImageDataURL` instead, since they can be large). All calls first check `a.ready()` since `a.repository` is nil until `startup` finishes opening the DB.
- **`internal/clipboard/`**
  - `types.go` — `Item`, `RawContent`, `AppInfo`, `ContentType` (text/url/image).
  - `parser.go` — classifies raw clipboard data and computes the SHA-256 dedup hash. Text hashing normalizes CRLF→LF before hashing (`HashText`) so Windows/macOS line-ending differences don't create duplicate entries. Images take priority over URLs/text; URL detection requires a *complete*, untrimmed `http(s)://` value (see `isHTTPURL`).
  - `service.go` — `Service.Capture(ctx, raw, source AppInfo)` parses + dedups + upserts, saving image bytes through the injected `ImageStore` (implemented in `app.go` as `diskImageStore`, content-addressed by hash under the app data dir — files on disk, not DB blobs) and tagging the item with whatever app currently owns focus. `Service.PreparePaste` sets `ignoreNextHash` before writing back to the OS clipboard so SailBoard's own paste-write doesn't get re-captured by the watcher and re-inserted as a "new" history item — this self-write guard is load-bearing; don't remove it when touching capture/paste flow.
  - `watcher.go` — `Watcher` polls injected `ReadText`/`ReadImage`/`Sequence`/`IsPaused` funcs on an interval (default 250ms); `Sequence` (backed by `GetClipboardSequenceNumber` on Windows, `NSPasteboard.changeCount` on macOS) lets it skip a full read on most ticks instead of naive diffing. Every OS-specific read is injected as a plain function from `app.go`, so this file has zero platform-specific code.
- **`internal/storage/`** — `Repository` wraps `modernc.org/sqlite` (pure-Go, no cgo). `Upsert` is the dedup entry point: on hash collision it just bumps `last_used_at` and returns the existing row (re-pinning duplicates to the top) instead of inserting. `Cleanup` enforces both retention-days and max-storage-bytes policies; favorited items are exempt from both. Settings are stored as loose key/value rows (`GetSettings`/`SaveSettings`), not a typed table. Schema changes after the initial `CREATE TABLE IF NOT EXISTS` block go through a versioned migration gated on `PRAGMA user_version` (see `migrateSourceIcon`) — **the initial `migrate()` SQL must never set `user_version` itself**; it did once, unconditionally, on every startup, which silently erased whatever a later migration had bumped it to and made that migration's `ALTER TABLE ADD COLUMN` re-run against a column that already existed, crashing every second launch. `TestMigrateIsIdempotentAcrossReopen` guards this regression — keep it passing when adding a new migration step.
- **`internal/platform/`** — the OS abstraction boundary. `types.go` defines the `Controller` interface (hotkey registration, foreground capture/restore, paste injection, active-app + icon lookup, monitor work-area geometry, clipboard image/richtext/files read/write, file thumbnails, autostart, tray icon, single-instance lock, cross-process settings notification) plus a `HotkeySpec`/`ParseHotkeySpec` that's pure string logic (no build tag, unit-testable directly). `controller_defaults.go` (`!windows`) holds the shared `stubController` type + its no-op method bodies; `controller_stub.go` (`!windows && !darwin` — i.e. neither of the two platforms this project targets) is the thin `New()` that returns it as-is. Windows and macOS each have their own `New()` (`controller_windows.go`/`controller_darwin.go`) returning a struct that embeds `stubController` and overrides every method with a real implementation — both platforms now implement all 26 Controller methods, none left stubbed.

  `controller_windows.go` + the other `*_windows.go` files are the real Win32 implementation, built entirely on raw `syscall.NewLazyDLL` calls (no cgo) — three thread/coordinate-system gotchas worth knowing before touching this code, all found by actually running the built exe and driving it with real key/screenshot round-trips rather than trusting compilation:
  - **`RegisterHotKey`/`UnregisterHotKey`/`DestroyWindow` must be called from the exact OS thread that owns the target window**, not just any thread that has the right HWND. See `winmsg_windows.go`'s `runSync`/`wmExecute` job-queue, which marshals those calls onto the dedicated, `runtime.LockOSThread`-pinned message-loop goroutine that also owns the hidden window and pumps `WM_HOTKEY`/tray messages.
  - **A window shown from a background-process goroutine (our hotkey handler) doesn't reliably receive OS keyboard focus** just because `runtime.WindowShow`/Wails' own `SetForegroundWindow` call ran — Windows' foreground-lock exemption doesn't reliably survive the goroutine hop. `foreground_windows.go`'s `focusSelf` (via `AttachThreadInput`) forces it; `app.go`'s `ShowWindow` calls it after every show, and the frontend *also* re-`.focus()`s the search input on every `window:shown` event since focusing the top-level HWND doesn't automatically hand focus to the embedded WebView2 control.
  - **`MonitorFromPoint` takes a `POINT` *by value*** — the x64 ABI packs that 8-byte struct into one register (low32=x, high32=y), not two separate syscall args; and **Wails' `runtime.WindowSetPosition` treats (x,y) as an offset from the window's *current* monitor's work-area origin, not absolute screen coordinates** (only looks correct on a single primary monitor, whose origin is (0,0)). Both bit the multi-monitor positioning path; `screen_windows.go` and `foreground_windows.go`'s `positionSelf` (a direct `SetWindowPos` call, bypassing Wails' quirky one) fix them respectively — `app.go`'s `ShowWindow` always positions via `platform.Controller.PositionSelf`, never `runtime.WindowSetPosition`.

  Image bytes cross the Win32 boundary as re-encoded PNGs (`clipboard_image_windows.go` converts CF_DIB ↔ PNG); `decodeDIB` is pure parsing and is unit-tested via hand-built DIB buffers, without touching the real clipboard.

  `controller_darwin.go` + the other `*_darwin.go`/`.m`/`.h` files are the real Cocoa/Carbon implementation, using cgo — unlike Windows, avoiding cgo buys nothing here (Wails' own darwin frontend already forces `CGO_ENABLED=1`), so each capability is a thin Go file plus a matching `.m`/`.h` pair calling AppKit/Carbon/ApplicationServices directly. Five gotchas worth knowing before touching this code, every one found only by running the packaged `.app` on real hardware — none were visible from reading the code or from `go vet`/`go build` succeeding:
  - **Spawning a goroutine from code that is itself running as a synchronous native callback (Carbon's hotkey handler, an AppKit menu-item's target-action, a distributed-notification block) reliably SIGSEGVs the first time that goroutine calls back into Cocoa/GCD.** The identical `ShowWindow`→`go func(){ SlideReveal }()` code runs fine when triggered from an ordinary goroutine (e.g. the 300ms post-startup auto-show) and crashes when triggered from inside one of those native callback stacks. Every entry point that's reached from a native callback — `hotkey_darwin.go`'s `sbHotkeyFired`, `tray_darwin.go`'s `sbTray*Clicked`, `ipc_darwin.go`'s `sbSettingsChangedNotification`/`sbShowMainNotification` — routes through `controller_darwin.go`'s `darwinMainThreadCallbacks` channel and its one persistent, ordinarily-`go`-started dispatcher goroutine instead of running the handler in place, specifically to avoid this. Don't add a new native-callback entry point that calls a Controller method directly; route it through that channel too.
  - **This package's Objective-C files are all compiled without ARC** (no `-fobjc-arc`), matching how the rest of the project avoids extra build machinery — which means a "convenience constructor" return value (anything not prefixed `alloc`/`new`/`copy`, e.g. `NSStatusBar.statusItemWithLength:`) is autoreleased, and assigning it to a `static` C variable meant to outlive the current `@autoreleasepool` block does **not** retain it. `tray_darwin.m`'s status item vanished silently (no crash, no error — it was just never visible) until an explicit `retain` was added. Any future "build a Cocoa object once, keep it in a static, reuse it" code needs the same explicit retain.
  - **Wails' own `AppDelegate.m` unconditionally sets `[NSApp setActivationPolicy:NSApplicationActivationPolicyRegular]`** in `applicationWillFinishLaunching`, silently overriding `LSUIElement` in Info.plist (which is otherwise the standard way to hide an app's Dock icon) — there's no supported Wails-level option to disable this in v2.10.2 (`pkg/options/mac.Options` has a commented-out `ActivationPolicy` field). `tray_darwin.go`'s `ShowTray` calls `darwinHideDockIcon` (`controller_darwin.m`'s `sb_set_activation_policy_accessory`) *after* creating the status item to switch back to Accessory — deliberately in that order, since switching first and creating the status item under Accessory policy left it unrendered (confirmed by A/B testing, not fully root-caused). Verify with `lsappinfo list | grep -A5 SailBoard` and check `type=` (`UIElement` = correct, `Foreground` = the override won) — more reliable than eyeballing the Dock.
  - **`pbpaste`'s output encoding depends on `LANG`/`LC_ALL`**, and Wails' own macOS clipboard text read/write (`internal/frontend/desktop/darwin/clipboard.go`) shells out to `pbpaste`/`pbcopy`. A GUI `.app` launched from Finder/LaunchServices inherits neither env var (unlike a shell-launched process) — confirmed by hand, `pbpaste` under an env with no `LANG` emits legacy GBK-ish bytes for CJK clipboard content instead of UTF-8. `main.go`'s `fixDarwinLocale()` sets both to `en_US.UTF-8` at the very start of `main()`, before Wails ever shells out; `os/exec` children inherit the current process's env by default so one `os.Setenv` fixes every `pbpaste`/`pbcopy` call for the process's lifetime.
  - **A `*os.File` kept only in a local variable doesn't stay open for "the rest of the process"** the way a raw fd would — `os.File` registers a runtime finalizer that closes its fd when the object is garbage collected, and a long-running process (`wails.Run()` allocates continuously) *will* eventually GC an unreferenced one. `singleinstance_darwin.go`'s `flock`-based single-instance lock silently released itself mid-run this way until the winning `*os.File` was stashed in a package-level var — a short-lived standalone test program never lived long enough to trigger a GC cycle and expose the bug, which is why it looked correct in isolation. Keep this in mind for any future "hold a lock/fd for the process's lifetime" code — you must keep a live reference, not just avoid calling `Close()`.
- **`internal/webpreview/`** — URL title/favicon fetch. Split into pure parsing (`ExtractTitle`, `ExtractFaviconURL` — regex-based, unit-tested with no network) and `Fetch`, which adds a hard 3s timeout. Called only on demand from `App.PreviewURL`, never from the watcher, so a slow site can never block clipboard capture.
- **`main.go`** — besides the usual Wails options, sets `Windows.WebviewIsTransparent` + `WindowIsTranslucent` + `BackdropType: windows.Acrylic` with a fully transparent `BackgroundColour`. This is what makes the panel real native frosted glass (genuinely blurring whatever's behind the window) rather than a flat translucent colour — the CSS glass panel in `App.css` is layered on top of this native backdrop, not a substitute for it. `DisableFramelessWindowDecorations` turns off Windows 11's automatic rounded-corner/shadow on frameless windows, which otherwise makes a full-width bottom sheet read as a floating card. On macOS, `fixDarwinLocale()` (see the `pbpaste`/`LANG` gotcha above) runs first thing in `main()`, and `trayIconPNG` picks between two embedded images (`logo.png`/`logo_tb.png`) by `GOOS` — macOS gets the transparent-background one since the menu bar isn't opaque the way the Windows taskbar tray is.
- **`frontend/src/App.tsx`** — main React UI (card rail, search, settings modal, pause toggle, keyboard nav for ←/→/Enter/Esc). `ImageCardContent.tsx` and `UrlCardContent.tsx` are small per-card components that lazily fetch `GetImageDataURL`/`PreviewURL` on mount rather than inlining that data into the list response. Calls generated Wails bindings from `frontend/wailsjs/go/main/App` (not checked in — regenerated by `wails dev`/`wails build`/`wails generate module`) and subscribes to the `history:changed`, `paused:changed`, and `window:shown` backend events. The panel's reveal is a pure CSS transform driven by a `visible` boolean toggled on `window:shown` (see `.shell`/`.sheet` in `App.css`): it starts translated fully off-screen and slides up, and `requestHide()` reverses that and only calls the backend `HideWindow` after the transition duration elapses — keep `HIDE_ANIMATION_MS` in sync with that CSS duration if either changes. Card deletion follows the same pattern (`exitingIds` + `DELETE_ANIMATION_MS` before the actual `DeleteItem` call) so the card animates out instead of vanishing instantly. **Keydown handling note**: `Escape` is handled *before* the "don't hijack keys while typing in the search input" guard — it must always work (clear search, then close), unlike arrow-key navigation which is deliberately suppressed while the search `<input>` has focus so it doesn't fight normal text editing. Digit keys 1-9 are *not* a card quick-select shortcut (removed 2026-08-24 at the user's request) — they fall through to the same "unhandled printable character focuses the search box" path as any other letter.

## Working within this codebase

- Any change must keep `go build`/`wails build` succeeding — "always compilable and runnable" is the top priority, not feature completeness.
- Add a test alongside any new module, matching the existing style (`parser_test.go`, `service_test.go`, `repository_test.go`, `hotkey_test.go`, `clipboard_image_windows_test.go`, `webpreview_test.go`). For native-syscall/cgo-heavy code (hotkey registration, tray, active-window lookup, real clipboard reads — on either platform) automated tests aren't practical (they need a live desktop/message-loop or run-loop session) — pull the pure logic out into a testable function (like `decodeDIB`, `ParseHotkeySpec`, `keyToVK`/`darwinKeyToVK`) instead of trying to unit test the syscalls/cgo calls directly, and validate the native glue by actually running `wails build` and launching the built exe/`.app` (more than once, to catch state-across-restart bugs like the migration one above, or GC-timing bugs like the flock one above that a short-lived run won't trigger). Every real native-layer bug found so far on either platform (see the platform bullet above) was caught this way, not by reading the code — trust the round-trip over the syscall/cgo call looking plausible. On macOS specifically, `go vet`/`go build` succeeding proves nothing about runtime behavior (see the five gotchas above, none of which were compile-time detectable); cross-compiling for the *other* platform (`GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build`, no Windows machine needed) after a macOS-side change is cheap insurance that it didn't touch the Windows build path.
- If you're driving the built exe over an RDP session to verify UI/interaction changes (screenshot via `Graphics.CopyFromScreen`, keys via `keybd_event`/`SendInput`), keyboard-injected input is reliable, but synthetic mouse clicks (`mouse_event` and `SendInput` alike) have not reliably reached the WebView2 surface in that environment — a known category of remote-session + GPU-composited-surface flakiness, not necessarily an app bug. Verify keyboard-driven flows this way freely; treat a failed synthetic mouse click as inconclusive rather than a confirmed regression, and prefer a real local mouse for that specific check.
- Platform-specific behavior must go behind `internal/platform.Controller` (or `clipboard.Watcher`'s injected funcs) — don't hardcode a single OS's API into `internal/clipboard` or `internal/storage`. Windows-only files (`*_windows.go`) and macOS-only files (`*_darwin.go`/`.m`/`.h`) must never touch each other's build — verify with the cross-compile check above before considering a platform-specific change done.
- Out of scope: OCR, AI search/summarization, auto-categorization, multi-device or cloud sync, accounts, rich text editing, clipboard workflows/scripting, browser extensions. Linux is out of scope entirely (not just deferred) — the generic `!windows && !darwin` stub exists only so the module still compiles elsewhere, not as a supported target.
